# BookWheel Accessibility Audit

**Date:** 2026-09-04
**App version tested:** 2.13.0 (live instance at http://localhost:32700)
**Standard:** WCAG 2.1 Level AA
**Account used:** `a11yuser` (non-admin)
**Method:** Automated browser testing (Chrome DevTools MCP, accessibility-tree snapshots, `getComputedStyle` contrast sampling) plus manual source review of `index.html`, `js/app.js`, `js/i18n.js`, `css/site.css`.

---

## Executive Summary

BookWheel is a small vanilla-JS SPA that, unusually for a hand-rolled app with no accessibility framework, demonstrates a genuinely strong and *deliberate* accessibility baseline. The codebase shows clear evidence of accessibility-aware engineering: a working skip link, correctly associated and announced form errors, a keyboard-operable canvas widget with a text-based alternative to the visual wheel, full WAI-ARIA Authoring Practices tab patterns (roving tabindex, arrow-key navigation, `aria-selected`), native `<dialog>` modals instead of hand-rolled focus traps or blocking `alert()/confirm()`, a `prefers-reduced-motion` implementation that reaches into both CSS and the spin-timing logic in JavaScript, and a graceful, announced fallback when barcode scanning isn't supported.

Against WCAG 2.1 AA, the app is **close to compliant**. The issues found are narrow and mostly Level AA/best-practice in nature rather than fundamental Level A breakdowns:

- One clear **1.4.3 Contrast (Minimum)** failure: primary button text in the **light theme** measures 4.10:1, under the 4.5:1 AA threshold for normal-weight-size text (verified against live computed styles, not just source CSS).
- A **focus-order anomaly** inside the delete-confirmation dialog, where Tab cycling passes through an invisible stop on `<body>` between the two buttons.
- The delete-confirmation dialog **defaults focus to the destructive "Remove" button** rather than "Cancel," which is a safety/best-practice concern more than a strict SC violation.
- A couple of minor semantic nits (a stray `banner` landmark nested inside a modal dialog; icon-badge accessible-name reliance on `aria-label` for a non-interactive `<span>`, which some screen readers may not honor consistently).

None of the findings are blocking for a screen-reader or keyboard-only user to complete the core tasks (log in, add/edit/remove a book, spin the wheel, change settings, review stats). The dark and high-contrast themes comfortably exceed AA (and mostly AAA) contrast requirements everywhere sampled.

**Overall assessment: Substantially conformant with WCAG 2.1 AA, with one confirmed contrast failure (light theme buttons) and a small number of moderate/minor issues to remediate.**

## Findings

### 1.4.3 Contrast (Minimum) — Level AA

**[Moderate] Primary button text fails AA contrast in the light theme**

All primary (non-`.secondary`) buttons render white text (`#ffffff`) on the `--accent` background (`#0284c7`) at `font-size: 16px; font-weight: 700`. 16px bold is 12pt bold, below WCAG's "large text" threshold (14pt/~18.7px bold or 18pt/24px regular), so the 4.5:1 normal-text ratio applies.

Verified two ways:
- Computed mathematically from the theme's CSS custom properties (`css/site.css` lines 27-50): **4.10:1**.
- Confirmed live via `getComputedStyle` on the actual `#spinBtn` element in the running app: `color: rgb(255,255,255)` on `background-color: rgb(2,132,199)`, `font-size: 16px`, `font-weight: 700` — same **4.10:1** result.

This affects every accent-colored primary button in the light theme: Log in, Add, Spin, Save, Create user, Import File, Download JSON, Copy link, Set password, etc.

For comparison, the same text/background pair in the other two themes passes comfortably:
| Theme | Primary button text ratio | Result |
|---|---|---|
| Dark (default) | 8.95:1 | Pass |
| Light | **4.10:1** | **Fail** (needs 4.5:1) |
| High-contrast | 19.56:1 | Pass |

Secondary buttons, body text, muted text, and error/danger text all passed the applicable AA thresholds in all three themes (see the Color Contrast section below for full figures).

**Recommendation:** darken `--accent` slightly for the light theme (e.g., toward `#026a9e`/`#015e8c`) or switch `--button-primary-text` to a dark color in light mode; re-verify the ratio ≥ 4.5:1.

### 2.4.3 Focus Order — Level A

**[Minor–Moderate] Stray focus stop on `<body>` inside the delete-confirmation dialog**

Opening the "Remove book" dialog focuses the `Remove` button first (see finding under 3.3 below). Pressing Tab from there does **not** move directly to `Cancel` — it lands on `document.body` first, then a second Tab reaches `Cancel`, and a third returns to `Remove`. Confirmed by tracking `document.activeElement` through each Tab press:

```
Remove (initial focus) → Tab → <body> → Tab → Cancel → Tab → Remove
```

The dialog does remain modal throughout (`dialog.open` stayed `true`, and the interstitial `document.activeElement` — `<body>` — is not part of the page content behind the modal, so keyboard users cannot escape into the background page). But a screen-reader or keyboard user tabbing through a 2-button dialog encountering an unlabeled, invisible stop is disorienting, and it indicates the browser's native modal focus-wrap isn't cleanly cycling between just the dialog's two focusable elements (likely because the dialog has only two focusable elements and no explicit `inert`/focus-trap handling beyond `showModal()`).

**Recommendation:** add an explicit `keydown` Tab-trap handler for dialogs with very few focusable elements (wrap from last to first and vice versa) rather than relying solely on native `<dialog>` behavior, or confirm this is fixed by testing again after a Chromium update.

### 3.2/3.3 — Best practice: default focus on destructive action

**[Minor] Delete-confirmation dialogs focus the destructive button by default**

In `js/app.js`, `openDialog(deleteDialog, confirmDeleteBtn)` explicitly passes the destructive **"Remove"** button as the element to focus when the dialog opens (same pattern likely applies to `deleteUserDialog`, admin-only). A keyboard user who instinctively presses Enter/Space right after triggering the delete flow (e.g., from muscle memory) will immediately confirm an irreversible removal rather than landing on the safer "Cancel" default.

This is not a strict WCAG failure, but it runs counter to the common UX/accessibility best practice (and the intent behind WCAG's caution around destructive, hard-to-reverse actions) of defaulting focus to the non-destructive option in confirmation dialogs.

**Recommendation:** default focus to the `Cancel` button instead (`openDialog(deleteDialog, cancelDeleteBtn)`), keeping `Remove` reachable via Tab.

### 1.3.1 Info and Relationships — Level A

**[Minor] Stray `banner` landmark nested inside a modal dialog**

The Settings dialog's `<header class="user-management-header">` (wrapping the "Settings" `<h2>`) is not a descendant of `<main>`, `<article>`, `<aside>`, `<nav>`, or `<section>` — its only ancestor is a plain `<div>` inside `<dialog id="settingsDialog">`. Per the HTML-AAM mapping, a `<header>` outside those sectioning elements is exposed with the implicit ARIA role `banner`, regardless of nesting inside a dialog. This was confirmed in the accessibility-tree snapshot (`uid banner → heading "Settings"`).

A `banner` landmark is meant to represent page-level identifying content (logo, site title, global nav) — having one appear inside a modal is unexpected for landmark-based navigation and could confuse users who jump by landmark region.

**Recommendation:** wrap the dialog title in a plain `<div>` instead of `<header>`, or add `role="presentation"` to neutralize the implicit banner role.

**[Minor / needs live-AT verification] Book-type badge relies on `aria-label` on a non-interactive `<span>`**

Each book row's type icon (📖/📱/🔖) is rendered as `<span class="book-type-badge" aria-label="Physical" title="Physical">📖</span>` — the `aria-label` was confirmed present and correctly localized via direct DOM inspection. However, this element has no ARIA role (default `generic`) and is not focusable/interactive. `aria-label` support on plain inline text spans is inconsistent across real assistive technology (some screen readers announce the label; others read the literal glyph or its Unicode name, e.g. "open book emoji," particularly under "read by character/word" navigation rather than "read by object"). Chrome's own accessibility-tree snapshot rendered this node as a raw `StaticText "📖"` rather than a named node, which is at least circumstantial evidence of inconsistent exposure.

**Recommendation:** verify with a real screen reader (NVDA/JAWS/VoiceOver). If the label isn't reliably announced, switch to `aria-hidden="true"` on the glyph plus a separate visually-hidden (`.sr-only`) text node carrying the label, matching the pattern already used elsewhere in the app (e.g., `wheelBooksSrList`).

### 4.1.2 Name, Role, Value — Level A (positive, with one caveat)

Icon-only *buttons* (Settings ⚙, Stats 📊, Scan barcode 📷, Theme toggle) are implemented correctly: the glyph `<span>` carries `aria-hidden="true"` and the parent `<button>` carries a real `aria-label` (and matching `title`) — this is the correct pattern and was verified both in source and in the live accessibility tree (e.g., `button "Settings"`, `button "Scan ISBN barcode"`). The one exception is the non-interactive book-type-badge `<span>` described above, which uses the same `aria-label` technique but outside of an interactive/landmark context where support is less reliable.

### 2.2.2 Pause, Stop, Hide — Level A (informational)

**[Low] Toasts auto-dismiss after ~2.6s with no way to pause or replay them**

`showToast()` (`js/app.js`) removes the toast element after a fixed 2600ms + 260ms fade, with no pause-on-hover/focus and no persistent history. This is Low severity because the toast's content generally duplicates a persisted, still-visible status message elsewhere in the DOM (e.g., `#bookMessage`, `#selectedBook`), so no information is exclusively lost when the toast disappears — but it's worth confirming that this is true for every toast call site, since a toast whose message exists *only* in the transient toast would fail 2.2.1/2.2.2 for users needing more time to read it.

### Functional note (not a strict a11y defect)

While testing, spinning the wheel shortly after adding a book (with a large pre-existing seeded library of 17 books already present on the `a11yuser` account) produced the message *"Selected book was not found on the current wheel"* — an apparent client/server data race rather than an accessibility bug. It's noted here only because the fallback message, while itself properly announced via the `aria-live="polite"` region on `#selectedBook`, could give assistive-technology users an inaccurate account of what actually happened. Worth a functional follow-up outside the scope of this audit.

## Positive Observations

- **Skip link works as intended.** `.skip-link` is off-screen by default (`top: -44px`) and moves on-screen (`top: 10px`) on `:focus-visible`. Verified live: the first Tab press from page load lands on the link and its bounding box becomes visible (`top: 10`, within viewport).
- **Login error is properly identified and announced.** `#loginError` uses `role="alert"`, `aria-live="assertive"`, `aria-atomic="true"`, *and* both `#username`/`#password` carry `aria-describedby="loginError"`. Verified live with a deliberately wrong password: the accessibility tree showed the textboxes gaining a `description` of "Invalid username or password." alongside the `alert` node — this satisfies both 3.3.1 (Error Identification) and 4.1.3 (Status Messages).
- **Password fields use correct semantics/autocomplete.** `type="password"` with `autocomplete="username"` / `"current-password"` on login and `"new-password"` on the reset-password form (helps password managers and satisfies 1.3.5 Identify Input Purpose).
- **Heading hierarchy is logical with no skipped levels**: `h1` "Book Wheel Login" (pre-auth) / `h1` "Book Wheel" (app shell) → `h2` "Spin wheel", `h2` "Active books" → `h3` "No books yet" / stats headings. Verified via accessibility-tree snapshots at each screen.
- **The spin wheel is fully keyboard-operable and has a non-visual result path.** The `<canvas>` has `tabindex="0"`, `role="button"`, and an `aria-label` that literally documents the interaction ("Book selection wheel. Press Enter or Space to spin."). Source confirms both `Enter` and `Space` (`" "`) call `spinBtn.click()`. Separately from the canvas, an `.sr-only` `<ul id="wheelBooksSrList">` lists every book currently on the wheel by number, and `#wheelSummary` / `#selectedBook` are `aria-live="polite"` regions that announce the book count and the spin result — so a screen-reader user never has to rely on the canvas's visual highlight to know what's on the wheel or what was picked.
- **Non-admin restrictions are correctly enforced in the UI, not just the API.** As `a11yuser` (non-admin), the "Manage users" settings tab is absent entirely (not merely disabled/hidden-but-focusable), and the Stats dialog's "All Users (Admin)" section is likewise absent — both confirmed via accessibility-tree snapshots showing no trace of those nodes.
- **Modals use native `<dialog>` + `showModal()`, not hand-rolled overlays or blocking `alert()/confirm()`.** This was specifically checked in source before interacting with the delete flow (per the task's constraint) — `deleteDialog` is a real `<dialog>`, so `Escape` closes it, and it participates in the browser's native top-layer/modal semantics. Confirmed live: Escape closes the dialog and focus returns to the row's "Remove book" trigger button (`dialogFocusReturnMap` correctly restores focus via the dialog's `close` event).
- **Settings/Import-Export/Stats tab groups implement the full WAI-ARIA Tabs pattern.** `role="tablist"`/`"tab"`/`"tabpanel"`, `aria-selected`, roving `tabindex` (`0`/`-1`), and `aria-controls`/`aria-labelledby` pairing are all present in source and verified live. Arrow-key navigation (`ArrowLeft`/`ArrowRight`, plus `Home`/`End` per source) moves focus **and** activates the corresponding panel — verified live in the Settings dialog (ArrowLeft/ArrowRight correctly moved between "Preferences" and "Import / Export").
- **Language switching updates document semantics correctly.** Selecting "Español" updates `<html lang>` from `en` to `es` (verified via `document.documentElement.lang`), and dynamic `aria-label`s update too — e.g., the theme-toggle button's label changed to a fully translated, state-aware string ("Cambiar a Modo de alto contraste" — "Switch to High-contrast mode"), not just its visible glyph.
- **Barcode scanning degrades gracefully and accessibly.** In this automated/headless environment the `BarcodeDetector` API is unavailable; clicking "Scan ISBN barcode" does **not** attempt to open a camera stream or throw — it immediately shows "Barcode scanning is not supported on this device or browser." via the same `role="status"`/`aria-live="polite"` message element used for other book-form feedback, with `aria-describedby` correctly pointing both title and ISBN fields at it. No native permission prompt or dialog was triggered.
- **Client-side and server-side validation errors are both associated and announced.** Submitting an invalid ISBN surfaced "The provided ISBN is not valid." via `#bookMessage` (`role="status"`, `aria-live="polite"`), which the title/ISBN inputs reference via `aria-describedby`. Native browser required-field validation (empty title) also produced an accessible `alert` with focus moving to the invalid field.
- **`prefers-reduced-motion` is honored in both CSS and JavaScript**, not just one layer. `css/site.css` collapses all animation/transition durations to near-zero under the media query, and separately, `js/app.js` reads `window.matchMedia('(prefers-reduced-motion: reduce)')` to cut the wheel spin from 5 full rotations over 4200ms down to 1 rotation over 120ms — a deliberate, functional accommodation beyond just suppressing CSS animation.
- **Focus-visible indicators are explicitly styled and consistent** across `button`, `input`, `.book-title-btn`, and `#wheelCanvas` in the default rule set, plus a dedicated higher-contrast (3px, `--accent`-colored, 2px offset) override for the high-contrast theme. No global `outline: none` reset exists; the one localized `outline: none` (admin-only "Create user" panel inputs) is paired with an equivalent visible `box-shadow` focus ring, so it's a substitution, not a removal.
- **Stats canvas bar chart has both a text alternative and a genuine data table.** `<canvas id="statsChartCanvas" role="img" aria-label="Spin frequency bar chart">` gives the canvas a name, and directly below it a real `<table>` (`#statsTable`) with `<thead><th>` column headers reproduces the exact same rank/book/spins/percentage data — so screen-reader users get full access to the underlying numbers, not just a generic chart label. The "Book Lists" tab (Unique Books Spun / Never Spun) is plain, fully accessible list markup.
- **Toasts and status messages don't rely on color alone.** `.toast-success`/`.toast-error`/`.toast-info` differ only by a subtle border tint, but the announced *text* itself always states the outcome (e.g., "Book added.", "The provided ISBN is not valid."), so meaning isn't conveyed by color alone.
- **Cover-image `alt` text is descriptive**, e.g. `alt="Cover of To Kill a Mockingbird"`, generated per book rather than a generic "cover" or empty string.
- **Contrast is strong everywhere except the one flagged case.** See table below — body text, muted/secondary text, secondary-button text, danger/error text, and UI-component-level accent usage all clear their respective AA thresholds in all three themes, and the high-contrast theme clears AAA thresholds across the board.

## Color Contrast — Method and Full Results

**Method:** Contrast ratios were computed using the standard WCAG relative-luminance formula against the theme colors defined as CSS custom properties in `css/site.css` (`:root`, `[data-theme="light"]`, `[data-theme="high-contrast"]`), executed as JavaScript in the live page. The most significant pairing (primary button text) was additionally cross-checked against `getComputedStyle()` output from a real rendered button (`#spinBtn`) to confirm the source-CSS values match what's actually painted. This is a mathematically exact method for solid-color pairs; it does not account for gradients, `color-mix()` blends used in some secondary/decorative surfaces, or anti-aliasing — those were spot-checked by reading the relevant CSS but not independently re-rendered pixel-by-pixel.

| Pair | Threshold | Dark | Light | High-contrast |
|---|---|---|---|---|
| Body text on card background | 4.5:1 | 14.33:1 ✅ | 17.85:1 ✅ | 21.00:1 ✅ |
| Muted/secondary text on card | 4.5:1 | 6.99:1 ✅ | 7.58:1 ✅ | 16.67:1 ✅ |
| Body text on page background | 4.5:1 | 14.42:1 ✅ | 16.61:1 ✅ | 21.00:1 ✅ |
| Accent color on card (UI component / focus ring use) | 3:1 | 8.28:1 ✅ | 4.10:1 ✅ | 19.56:1 ✅ |
| **Primary button text on accent background (16px/700)** | **4.5:1** | 8.95:1 ✅ | **4.10:1 ❌** | 19.56:1 ✅ |
| Secondary button text on secondary background | 4.5:1 | 8.36:1 ✅ | 12.02:1 ✅ | 17.40:1 ✅ |
| Danger/error text on card | 4.5:1 | 6.41:1 ✅ | 4.83:1 ✅ | 7.57:1 ✅ |
| Input text on input background | 4.5:1 | 15.12:1 ✅ | 17.06:1 ✅ | 21.00:1 ✅ |
| Disabled primary button (opacity-reduced) text vs. its own background | n/a (exempt) | 3.96:1 | 2.27:1 | 13.84:1 |

Disabled-control contrast is included for completeness only — WCAG 1.4.3 explicitly exempts inactive/disabled UI components, so the sub-3:1 light-theme figure is informational, not a finding.

## Recommendations

1. **Fix the light-theme primary button contrast** (Moderate priority). Darken `--accent` for `[data-theme="light"]` or use a darker `--button-primary-text`; re-verify ≥ 4.5:1.
2. **Default delete-confirmation dialogs to focus "Cancel," not the destructive button** (Minor priority, quick fix — swap the `preferredFocusElement` argument in `openDialog()` calls for `deleteDialog`/`deleteUserDialog`).
3. **Investigate the stray `<body>` focus stop inside 2-button dialogs** (Minor–Moderate) — consider an explicit Tab-wrap handler rather than relying solely on native `<dialog>` focus containment.
4. **Neutralize the incidental `banner` role on the Settings dialog header** (Minor) — swap `<header>` for a plain `<div>`, or add `role="presentation"`.
5. **Verify book-type-badge and scanner-badge `aria-label` announcement with a real screen reader** (Minor) and fall back to `aria-hidden` + adjacent `.sr-only` text if unreliable.
6. **Audit all `showToast()` call sites** to confirm none carry information that isn't also available in a persisted, non-transient status element, given the fixed ~2.6s auto-dismiss.
7. **Extend the custom `:focus-visible` outline rule to `select` elements** for visual consistency with buttons/inputs/canvas, particularly in the high-contrast theme.
8. Consider a follow-up **manual screen-reader pass** (NVDA + Chrome, VoiceOver + Safari) covering the full task list in this audit, since automated accessibility-tree inspection is a strong proxy but not a full substitute for real AT behavior (see Limitations).

## Limitations

- **Camera-based barcode scanning could not be tested.** The test environment has no physical camera and the automated browser does not support the `BarcodeDetector` API, so only the *unsupported-device fallback path* was exercised (and found to be accessible). The actual live-scanning UI (video element, reticle overlay, "Flip camera," detection-in-progress state) was not exercised end-to-end and should be verified manually on a real device with a camera.
- **No real assistive technology (screen reader/switch device/voice control) was used.** All "announcement" and "accessible name" findings are based on (a) the Chrome DevTools accessibility-tree snapshot, which mirrors the platform accessibility API Chrome exposes, and (b) direct inspection of ARIA attributes in the DOM/source. This is a reliable proxy for *what AT would receive*, but actual behavior can still vary by screen reader and browser combination (this is explicitly called out for the book-type-badge finding above).
- **Color contrast was computed mathematically from CSS custom properties**, cross-checked against one live `getComputedStyle()` sample (the flagged primary-button case), rather than sampled pixel-by-pixel from a rendered screenshot for every pairing. `color-mix()`-based decorative surfaces (toast borders, some hover/gradient states) were not independently re-verified this way.
- **Admin-only screens were not tested beyond confirming their absence for a non-admin account.** "Manage users," user creation/deletion, and the Stats "All Users (Admin)" panel were out of scope per the test account constraints (`a11yuser` is non-admin) and were not evaluated for their own accessibility.
- **The password-reset-via-link flow was not tested**, since it requires an admin-issued setup token not available to this account.
- **Automated interaction surfaced a functional (not accessibility) data-race** during wheel spin testing (see "Functional note" above); this was not investigated further as it falls outside this audit's scope.
- Testing was performed against a live, shared-state instance; a pre-existing library of 17 seeded books plus one test book (`A11y Audit Test Book Alpha`) added by this audit remain on the `a11yuser` account.
