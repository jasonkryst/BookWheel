# Internationalization (i18n) Audit — BookWheel

**Date:** 2026-09-04
**Scope:** Frontend translations (`wwwroot/js/i18n.js`), backend translations (`Resources/SharedErrors*.resx`), locale negotiation (`Services/ApiMessageLocalizer.cs`, `Program.cs`), and UI code (`wwwroot/js/app.js`, `wwwroot/index.html`) for the three supported locales: English (`en`, default), Spanish (`es`), Polish (`pl`).
**Method:** Static analysis (structural key-parity diff of `i18n.js` and the three `.resx` files via a scratch Node script; targeted greps of `app.js`/`index.html`/`Program.cs`/controllers), plus live, read-only spot checks against `http://localhost:32700` using the `audituser` account (no books/users created, edited, or deleted).

---

## Executive Summary

BookWheel's i18n foundation is unusually solid for a project the README admits was machine-translated: the 224-key frontend catalog (`i18n.js`) and the 26-key backend catalog (`SharedErrors*.resx`) have **100% key parity** across `en`/`es`/`pl`, no empty values, and no broken interpolation placeholders. Locale persistence, `<html lang>` updates, and the `Accept-Language` plumbing between frontend and backend are all correctly wired for the *custom* domain-error localization path.

The gaps that exist are concentrated in three places, in descending order of severity:

1. **A real, live-confirmed locale desync**: ASP.NET Core's automatic model-validation errors (from `[Required]`/`[StringLength]` DataAnnotations on request DTOs) are never routed through `ApiMessageLocalizer` and come back in English regardless of the client's locale — while errors thrown by application/domain code *are* correctly localized. A user working entirely in Spanish or Polish will see a mix of translated and untranslated error messages depending on which validation layer rejects their request.
2. **No real pluralization logic.** Count-bearing strings use a bare `count === 1 ? singular : plural` split (or, in one case, no split at all), which is wrong for Polish's three-way plural system and, in one specific string, wrong for English and Spanish too.
3. **A handful of hardcoded, un-internationalized `aria-label` strings and locale-insensitive date/number formatting** — small in count but real gaps.

None of these are catastrophic — the app is usable end-to-end in all three locales — but they are concrete, reproducible gaps a native-speaker review pass should fix.

## Findings

### Critical / High

#### F1 — Framework-level (DataAnnotations) validation errors are never localized
**Severity: High — live-confirmed, most user-visible gap found.**

`BookWheel/Models/UpdateBookRequest.cs` (used by `POST /api/books`) uses plain DataAnnotations attributes with no custom `ErrorMessage`:

```csharp
[Required]
[StringLength(200, MinimumLength = 1)]
public string Title { get; set; } = string.Empty;

[StringLength(20)]
public string? Isbn { get; set; }
```

When ASP.NET Core's model binder rejects a request before the controller body runs, it returns its own `ValidationProblemDetails` with framework-generated messages. These never pass through `ApiMessageLocalizer.Localize()` — there is no code path that touches them at all.

**Live reproduction** (via `fetch` from the app's own origin, `Accept-Language: es`, no book created — request was rejected):

```
POST /api/books  Accept-Language: es
{"title":"","isbn":"not-a-valid-isbn-999999999999"}

→ 400 {"title":"One or more validation errors occurred.",
       "errors":{
         "Isbn":["The field Isbn must be a string with a maximum length of 20."],
         "Title":["The Title field is required.",
                   "The field Title field must be a string with a minimum length of 1 and a maximum length of 200."]
       }, ...}
```

Still entirely in English, despite `Accept-Language: es`.

By contrast, the exact same endpoint's **domain**-level ISBN check (`BooksController.cs:191-194`, `IsbnValidator.TryNormalize` failing on a well-formed-length-but-invalid ISBN) *is* localized correctly:

```
POST /api/books  Accept-Language: es
{"title":"Audit Test Title","isbn":"123-bad-isbn"}

→ 400 {"message":"El ISBN proporcionado no es válido."}
```

**Root cause:** `ApiMessageLocalizer` (`BookWheel/Services/ApiMessageLocalizer.cs`) is a hand-maintained `Dictionary<string,string>` keyed by exact English literal → resx key (`BookWheel/Services/ApiMessageLocalizer.cs:7-34`). It is only ever invoked explicitly inside controller action bodies and `catch` blocks (`_errors.Localize(...)`). ASP.NET Core's built-in automatic-validation short-circuit (triggered by `[ApiController]`'s automatic 400 response) happens in the MVC action-invocation pipeline *before* any controller code runs, so it never touches `_errors`. Whether the runtime *could* localize these via .NET's own `DataAnnotationsResources` satellite assemblies is a separate question (Culture is correctly set by `UseRequestLocalization` before `MapControllers()` — see F-Not-a-bug below) — in practice it doesn't, at least not for `es`/`pl` in this container image.

**User-facing consequence:** a Spanish- or Polish-UI user who submits an empty title or an over-length ISBN sees an English error message mixed in with an otherwise fully-localized UI (the frontend does have its own client-side `books.titleRequiredError` etc., but they only fire for client-side pre-validation — anything that reaches the server and gets rejected by DataAnnotations bypasses that too).

**Recommendation:** either (a) give every DataAnnotations attribute an explicit `ErrorMessage` that maps through `ApiMessageLocalizer` (requires catching `ValidationProblemDetails` uniformly, e.g. via a custom `InvalidModelStateResponseFactory` that runs values through `_errors.Localize()`), or (b) confirm/enable .NET's built-in localized DataAnnotations resources for `es`/`pl` in the deployed runtime and verify live. Add a regression test analogous to `ApiMessageLocalizerTests.Localize_HasNonEmptyTranslation_ForEverySupportedCulture` that hits the actual HTTP pipeline with a `[Required]` violation and asserts the response is not in English when `Accept-Language: es`.

#### F2 — One controller catch-block bypasses localization entirely
**Severity: High — inconsistent with every sibling catch block.**

`BookWheel/Controllers/AuthController.cs:165-173`, the `CorruptedDataException` handler for `/api/auth/login`:

```csharp
catch (CorruptedDataException ex)
{
    _logger.LogError(ex, ...);
    return StatusCode(StatusCodes.Status500InternalServerError, new { message = ex.Message });
}
```

This returns the raw, un-localized `ex.Message` directly. Every other `CorruptedDataException`/`InvalidOperationException` handler in the codebase (e.g. `BooksController.cs:98-101`, `AuthController.cs:198-208`) routes through `_errors.Localize(ex.Message)`. Since `CredentialDataCorrupted` *is* a cataloged key (`SharedErrors.resx`), this is very likely a simple oversight — the fix is a one-line change to wrap `ex.Message` in `_errors.Localize(...)`.

#### F3 — `"No books were provided to import."` is not in the translation catalog
**Severity: Medium-High — silent, permanent English fallback for a real validation path.**

`BookWheel/Controllers/BooksController.cs:113-116`:

```csharp
if (request.Books is null || request.Books.Count == 0)
{
    return BadRequest(new { message = _errors.Localize("No books were provided to import.") });
}
```

This exact string does not appear as a key anywhere in `SharedErrors.resx`/`SharedErrors.es.resx`/`SharedErrors.pl.resx`, nor in `ApiMessageLocalizer.KeysByEnglishMessage` (confirmed by reading the full 25-entry dictionary — it is not present). `Localize()`'s fallback behavior (`ApiMessageLocalizer.cs:40-43`) means this call silently returns the English string unchanged for every locale, forever, with no warning. Since `ApiMessageLocalizerTests` only iterates over `ApiMessageLocalizer.KnownMessageKeys` (i.e., it can only test what's already cataloged), this specific gap would not be caught by the existing test suite even though the suite's design intent is exactly to catch this class of bug.

**Recommendation:** add the missing resx key (e.g. `NoBooksProvidedToImport`) + es/pl translations, and add it to the dictionary. More durably: add a build-time or test-time check that scans controller source for `_errors.Localize("...")` call-site literals and asserts each one is a key in `ApiMessageLocalizer.KnownMessageKeys` — this would have caught F3 automatically.

### Medium

#### F4 — No real pluralization; Polish plural grammar is wrong for most counts
**Severity: Medium — grammatically incorrect Polish output, silently wrong.**

`i18n.js` has exactly one pluralized pair, `books.countOne` / `books.countOther`, selected by a bare binary check (`app.js` — the "N books total" summary line):

```js
const bookLabel = totalBooks === 1 ? t('books.countOne') : t('books.countOther', { count: totalBooks });
```

This binary split is correct for English and Spanish (both have simple singular/plural), but **Polish has three plural forms**: singular (1), "few"/paucal (2–4, and 22–24, 32–34, … but not 12–14), and "many"/plural (0, 5–21, 25–31, …). The Polish catalog only has one non-singular form, `countOther: '{count} książek łącznie'`, which is the *many*-form word ("książek"). For counts 2, 3, 4 (and 22–24, etc.) the grammatically correct word is "książki" (few-form), not "książek". So e.g. "3 books total" renders as **"3 książek łącznie"**, which a native Polish speaker would read as ungrammatical (correct: "3 książki łącznie").

Every other count-bearing string in the app has **no plural handling at all** — one fixed template is reused for every count, including 1:

- `wheel.summaryCount`: `'Wheel has {count} books.'` — for `count === 1` this renders "Wheel has 1 books." (wrong in English too, not just es/pl). Used at `app.js:257`, feeds the screen-reader-only `#wheelSummary` live region.
- `users.totalUsers`: `'{count} users'` (en) / `'{count} usuarios'` (es) / `'{count} użytkowników'` (pl) — used unconditionally whenever `totalCount !== 0` at `app.js:514-516`, so a single-user account badge reads **"1 users"** / **"1 usuarios"** / **"1 użytkowników"**, all grammatically wrong in their respective languages (should be "1 user" / "1 usuario" / "1 użytkownik").
- `users.removedUserMessage`: `'Removed user {username}. Deleted {count} books.'` — same "1 books" issue for a user with exactly one book.

**Recommendation:** introduce a small plural-selection helper in `i18n.js` (e.g. using `Intl.PluralRules(locale).select(count)` to pick `one`/`few`/`many`/`other` catalog variants) and expand `countOne`/`countOther`-style keys to the categories `Intl.PluralRules` reports for each locale (`en`/`es` only need `one`/`other`; `pl` needs `one`/`few`/`many`). This is the standard, low-effort fix and avoids hand-rolling Polish plural-form logic.

### Low

#### F5 — A few hardcoded `aria-label`s with no i18n hook
**Severity: Low — narrow, accessibility-adjacent, not user-facing to sighted users.**

Two attributes in `index.html` are set directly to English text with **no** `data-i18n-aria-label` companion attribute, unlike the ~15 other `aria-label`s in the file that are all correctly wired:

- `index.html:200`: `<div class="tab-row" role="tablist" aria-label="Import and export options">` — no translation key exists for this at all.
- `index.html:371`: `<canvas id="statsChartCanvas" ... aria-label="Spin frequency bar chart" role="img">` — same.

Both are always announced in English to screen-reader users regardless of the selected UI locale. (Contrast with `index.html:72`, `:77`, `:130`, `:146`, `:365`, all of which have the raw English text as a pre-JS fallback *and* a `data-i18n-aria-label`/`data-i18n-title` attribute that `i18n.js#applyStaticTranslations` overwrites on load and on locale change — that pattern is correct and intentional; F5's two instances are missing the second half of it.)

**Recommendation:** add `transfer.importExportOptionsLabel` and `stats.chartAriaLabel` (or similar) keys to all three locales, and wire `data-i18n-aria-label` on both elements.

#### F6 — Dates are formatted with the browser's locale, not the app's selected UI locale
**Severity: Low-Medium — real inconsistency, moderate impact.**

Every date-formatting call site uses `.toLocaleString()` / `.toLocaleDateString()` with **no locale argument**:

- `app.js:443` — `users.linkExpiresAt` interpolation: `expiresAt.toLocaleString()`
- `app.js:682` — `users.createdOn` interpolation: `createdDate.toLocaleDateString()`
- `app.js:2563` — `auth.linkExpiresAt` interpolation: `expiresAt.toLocaleString()`

Per MDN/ECMA-402, omitting the locale argument makes these default to the *browser's* runtime locale (`navigator.language` at the JS-engine level), which is independent of BookWheel's own `bookwheel-locale` selection. A user whose OS/browser is set to `en-US` but who has explicitly switched the app's language to Polish via the Settings dropdown will still see dates formatted the `en-US` way (e.g. `9/4/2026, 3:00:00 PM`) inside otherwise-Polish UI strings (e.g. `"Ten link wygasa 9/4/2026, 3:00:00 PM."`).

**Recommendation:** pass `window.BookWheelI18n.getCurrentLocale()` as the first argument, e.g. `expiresAt.toLocaleString(getCurrentLocale())`, or centralize via `Intl.DateTimeFormat(getCurrentLocale(), {...}).format(date)`.

#### F7 — Stats percentages/counts are not locale-aware numbers
**Severity: Low — cosmetic; current values are small integers so no visible difference today.**

`app.js:2424` builds the stats table row as `` `${book.percentage}%` `` and `makeSummaryCard` (`app.js:2270-2283`) sets `val.textContent = value` directly — neither goes through `Intl.NumberFormat`. For the integer/small-percentage values currently produced, this looks identical across `en`/`es`/`pl` (no thousands separators or decimals involved yet), so it's a latent rather than active gap — but if percentages ever get a decimal (Polish/Spanish use `,` as the decimal separator, not `.`) or counts grow into four digits (thousands-separator differs: `1,234` en vs `1.234`/`1 234` es/pl), the display would be wrong for es/pl. Worth fixing proactively with `Intl.NumberFormat(locale)` / `Intl.NumberFormat(locale, {style:'percent'})`.

#### F8 — Open dialogs are not re-rendered on locale change (one gap)
**Severity: Low — narrow edge case.**

The `bookwheel:locale-changed` handler (`app.js:2526-2539`) correctly re-renders the active-books list, user rows (if the Manage Users panel is open), the wheel accessibility summary, and the auth view — but does **not** re-render an open Stats dialog. In practice this is very low-impact since the Settings dialog (where the language switcher lives) and the Stats dialog are separate, mutually-exclusive dialogs, so a user can't be looking at stats and the language dropdown at the same time in the current UI — but if that ever changes, stats content would remain in the old locale until the dialog is closed and reopened.

### Not a bug (verified correct / intentional)

- **Backend locale negotiation is correctly wired for the custom error path.** `Program.cs:244-250` configures `UseRequestLocalization` with `en`/`es`/`pl` as supported cultures, registered before `app.MapControllers()` (`Program.cs:310`), so ASP.NET Core's default `RequestCultureProvider` chain (query string → cookie → `Accept-Language` header) resolves the culture before controller/localizer code runs. The frontend's `requestJson()` helper (`app.js:459-468`) sends `'Accept-Language': window.BookWheelI18n.getCurrentLocale()` on every API call that goes through it, keeping the two systems in sync for domain-level errors (confirmed live: `es` UI → `_errors.Localize()`-routed errors come back in Spanish; see F1 for the paths that *don't* stay in sync).
- Two raw `fetch()` calls (`app.js:2390`, `2471`, for `/api/stats` and `/api/stats/aggregate`) don't send `Accept-Language` and don't display server error text at all on failure (they `throw new Error()` with no message and show a fixed, already-translated `stats.loadError` string) — so the missing header has no user-visible effect for these two calls specifically.
- **Open Library book-lookup results are correctly left un-transliterated.** Titles/authors returned by `OpenLibraryBookMetadataLookupService` are passed straight into the DOM (`app.js` cover-preview and book-row rendering) with no translation layer — this is expected and correct; book metadata should reflect what the source catalog returns, not the UI locale.
- **RTL readiness (forward-looking, not a current gap).** `site.css` uses physical `left`/`right` properties in 9 declarations rather than logical properties (`inset-inline-start/end`, `margin-inline-*`). Since `en`/`es`/`pl` are all LTR, this has zero current impact — noted only because a future RTL locale would require converting these to logical properties.
- **Language-name select options are intentionally untranslated.** `index.html:237-239` shows `English` / `Español` / `Polski` — each language name in its own script, which is the standard, expected UX convention for a language picker (not a bug).

## Translation Completeness Report

### Frontend (`i18n.js`) — key-by-key structural diff

| Locale | Keys present | Missing vs. `en` | Orphaned (extra) | Empty values | Placeholder mismatches |
|---|---|---|---|---|---|
| en (baseline) | 224 | — | — | 0 | — |
| es | 224 | 0 | 0 | 0 | 0 |
| pl | 224 | 0 | 0 | 0 | 0 |

**Result: 100% structural parity.** No missing keys, no orphaned keys, no empty strings, and every `{placeholder}` token in an English string has an exact-match counterpart in both es and pl (verified programmatically across all 224 keys).

A small number of es/pl values are identical to their English counterpart; all are legitimate (cognates, loanwords, or symbols), not untranslated placeholders:

- `books.isbnLabel` = "ISBN" (es, pl) — ISBN is not a translated term in any of the three languages.
- `books.typeDigital` = "Digital" (es) — true cognate.
- `users.administratorLabel` / `users.roleAdmin` = "Administrator" (pl) — standard Polish loanword, correct.
- `users.adminCheckbox` = "Admin" (es, pl) — abbreviation, used identically.
- `transfer.importTab` = "Import" (pl) — standard Polish loanword, correct.
- `stats.tableRank` = "#", `stats.tablePct` = "%" (es, pl) — symbols, not words.

None of these are translation gaps.

### Backend (`SharedErrors*.resx`) — key-by-key diff

| Locale | Keys present | Missing vs. default | Empty values | Suspicious/placeholder-looking |
|---|---|---|---|---|
| default (en) | 26 | — | 0 | — |
| es | 26 | 0 | 0 | 0 |
| pl | 26 | 0 | 0 | 0 |

**Result: 100% structural parity.** All 26 `<data>` entries in `SharedErrors.resx` have a matching key with a non-empty, genuinely-translated (not copy-pasted English, not placeholder text) value in both `SharedErrors.es.resx` and `SharedErrors.pl.resx`. This is also enforced by an existing automated test, `ApiMessageLocalizerTests.Localize_HasNonEmptyTranslation_ForEverySupportedCulture`, which iterates every cataloged key and asserts the es/pl translation is both non-empty and different from the English source — a good regression guard, though it can only catch drift for keys that are already in the dictionary (see F3).

**Caveat on "completeness":** structural/key-level completeness is 100%, but **coverage** is not — F1 and F3 show that not every error-producing code path is routed through this catalog at all (framework validation errors, and one uncataloged string), so "100% of cataloged strings are translated" is true but doesn't mean "100% of user-facing error text is localized."

### Estimated overall completeness by locale

| Locale | Catalog completeness (both files) | Practical/runtime completeness (accounting for F1–F5) |
|---|---|---|
| es | 100% | ~92–95% (docked mainly for F1's framework-validation gap, which affects every ISBN/title-length validation error) |

These "practical completeness" figures are qualitative estimates based on the number and user-facing frequency of the gaps found, not a precise metric — they're meant to convey that the catalogs are fully translated but a meaningful slice of *runtime* error/count text still leaks English or ungrammatical Polish.

## Positive Observations

- **Perfect structural parity** across both the 224-key frontend catalog and the 26-key backend catalog, with zero missing keys, zero orphaned keys, zero empty values, and zero broken interpolation placeholders — a clean baseline that's easy to build on.
- **`Accept-Language` wiring is correct and live-verified** for the primary error-reporting path: switching the UI to Spanish and triggering the app's own ISBN-format validation (`BooksController.cs:191-194`) returns a correctly translated Spanish message end-to-end.
- **Locale persistence and switching UX are solid**: `bookwheel-locale` is persisted to `localStorage` (`i18n.js:4, 830`), `<html lang>` is updated both on initial load and on every `setLocale()` call (`i18n.js:831, 837`), and a `bookwheel:locale-changed` event drives re-rendering of already-mounted dynamic content (active books, user rows, auth view, wheel summary) so a locale switch doesn't require a page reload.
- **First-visit locale detection is sensible**: falls back through `localStorage` → `navigator.languages` (checking each entry, not just the first) → `en` default (`i18n.js:753-771`).
- **A real regression test already exists** (`ApiMessageLocalizerTests.cs`) specifically designed to catch backend translation drift — including a "coverage" test that iterates every cataloged key and both non-default cultures. This is above-average diligence for a project this size and should be extended (see F3's recommendation) rather than replaced.
- **The README is honest about translation provenance** (`README.md:77`: "Spanish and Polish translations were authored by the assistant as a first pass and have not been reviewed by native speakers") — this sets accurate expectations and explains why a couple of grammar nuances (F4) exist without anyone having dropped the ball.
- **Book-lookup metadata (titles/authors from Open Library) is correctly left unlocalized**, matching expected behavior for bibliographic data sourced from an external catalog.

## Recommendations (priority order)

1. **(F1)** Route ASP.NET Core's automatic model-validation (400) responses through `ApiMessageLocalizer`, or confirm the container image has the Spanish/Polish `DataAnnotationsResources` satellite assemblies wired up and re-verify live. This is the highest-impact fix — it affects the most common validation errors (empty title, over-length fields) on the most-used form in the app.
2. **(F2)** One-line fix: wrap the raw `ex.Message` in `AuthController.cs:172` with `_errors.Localize(ex.Message)` to match every sibling catch block.
3. **(F3)** Add the missing `NoBooksProvidedToImport`-style key to all three resx files and the `ApiMessageLocalizer` dictionary; consider a source-scanning test that fails the build if any `_errors.Localize("...")` call-site literal isn't a known key.
4. **(F4)** Adopt `Intl.PluralRules` for all count-bearing strings (`books.count*`, `users.totalUsers`, `wheel.summaryCount`, `users.removedUserMessage`) instead of the current binary/no-op splits — this is the correct, low-effort fix for both the English/Spanish "1 users" bug and the Polish few/many distinction.
5. **(F5)** Add `data-i18n-aria-label` + catalog keys for the two orphaned `aria-label`s (`index.html:200`, `:371`).
6. **(F6)** Pass `getCurrentLocale()` into every `.toLocaleString()`/`.toLocaleDateString()` call so displayed dates match the selected UI language, not the browser's own locale.
7. **(F7)** Use `Intl.NumberFormat(locale)` for stats percentages/counts proactively, before larger numbers or decimal percentages surface the current gap visibly.
8. **(F8)** Low priority: extend the `bookwheel:locale-changed` handler to re-render the Stats dialog's content if it happens to be open.
9. Once native-speaker review becomes available (per the README's own caveat), prioritize re-reviewing the Polish catalog first — the plural-grammar issue in F4 means Polish speakers are more likely to notice rough edges than Spanish speakers.

## Limitations

- This audit is static-analysis-plus-targeted-live-testing, not an exhaustive click-through of every UI state in all three locales. Deeply nested or rarely-hit UI states (e.g. every combination of dialog + error + locale) were not individually screenshotted.
- Live testing was done via direct `fetch()` calls from the browser console (same-origin, authenticated as `audituser`) rather than clicking through every form, to guarantee no mutation of shared state per the task's constraints — this validates the HTTP-level locale behavior precisely but doesn't confirm every pixel of client-side error-message rendering for each case.
- The "practical/runtime completeness" percentages in the Translation Completeness Report are qualitative estimates, not derived from an automated coverage metric — there is no existing instrumentation that counts how often each error path fires in production, so the estimate is based on code-path prevalence and reviewer judgment.
- Whether .NET's built-in `DataAnnotationsResources` ships/loads `es`/`pl` satellite resources in this specific container image was not root-caused beyond confirming the live behavior (English regardless of `Accept-Language`); F1's recommendation covers both possible underlying causes without requiring that distinction to be resolved first.
- This audit did not assess the PWA manifest, service worker cache strings, or Google Analytics integration for locale-related concerns, since none of those were in scope per the task brief.
- Concurrent audits were modifying the shared book list during this session (the active-book count changed from 4 to 11 between two page loads a few minutes apart) — none of that activity originated from this audit, and no book/user data was created, edited, or deleted by this audit's testing.
